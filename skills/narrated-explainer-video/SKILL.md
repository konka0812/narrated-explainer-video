# 口播科普动画

目标是让观众在听懂口播的同时，看懂对象、关系和变化。动画负责解释，字幕负责可读，画面文字负责强调。题材、语言、风格和发布平台由当前任务决定。

## 从当前进度开始

先查看用户给出的材料、现有工程和已确认的决定，再选择入口，不要求用户重走完整流程：

- **只有选题或观点**：整理一个核心问题、受众和结论，协助写自然可说的稿子。内容过多时建议聚焦或拆分，不擅自拆成多条视频。
- **只有稿子**：可以先做视觉方案与粗分镜。没有正式音频时，时间只是估算，不能宣称已经同步。
- **已有音频和字幕**：直接检查输入、确定时间轴、设计分镜，不按旧稿重新编排时间。
- **已有工程或预览**：定位反馈对应的镜头与时间段，保留仍有效的风格、素材和结构，针对问题修改。
- **要求发布交付**：核对最终输入与工程，完成相应成片、封面或文案。只做本次需要的交付物。

缺少信息时优先从材料和工程推断。仅在确实影响结果时询问，例如最终音轨版本不明。若用户明确要求先确认方案，提供具体方案后等待；已有授权或确认则继续，不逐步重复索要批准。

进入版式与时间轴实现前，明确**画幅与发布场景、时长依据、本次交付物**。已有工程和已确认要求优先；有最终旁白时，以实际时长安排，不为了套用目标时长而裁音频。缺少明确要求时先提出合适的默认方案并说明假设；若关键选择无法合理推断且会造成大量返工，再向用户确认。选题讨论、写稿等不依赖这些选择的工作可以继续。

## 进入制作前：检查并准备环境

当任务进入工程实现或预览阶段，先阅读 [环境检查与首次搭建](references/environment.md)。**如果选择 Remotion 但本机没有可用环境，先补齐运行环境、初始化工程、安装依赖并验证预览和测试帧，再制作整片。** 不能假定装了本 skill 就已经装好 Remotion。

区分缺少 Remotion 指导 skill、缺少 Node.js 等运行环境、缺少项目依赖、缺少工程这几种情况。已有工程优先复用并按锁文件安装，避免重新初始化或随意升级；只要求口播稿或视觉方案时，无需先安装软件。

## 1. 建立内容与时间基准

记录当前输入文件、音频时长、字幕范围、画幅、帧率、工程入口与目标交付。用户指定的最终版本优先于旧口播稿和旧导出。

- 保留字幕原文、序号和绝对时间。检查缺句、空字幕、倒序、重叠、过短显示和超出音频等情况；重叠也可能是有意设计，先判断。
- 字幕是分镜依据，音频是实际节奏依据。两者实质冲突时指出具体句子与时段，遵循用户指定的依据；不能悄悄改话、拉伸音频或挪字幕来掩盖问题。
- 时效性事实、数字、政策和新闻来源需要核实。若最终录音含有影响含义的错误，提出具体修正，不让画面与口播相互矛盾。
- 新音频或新字幕到来后，重新计算受影响时间段、字幕、转场和总帧数，检查后续镜头是否仍同步。

有 SRT 时可运行 [scripts/inspect_media.py](scripts/inspect_media.py)，生成可审阅的时间轴和输入警告。它只能做结构与时长检查，不能证明文字与发音一致。调用方法见 [实现与同步](references/production.md)。

## 2. 先确定可判断的视觉方向

视觉方案同时说明：主视觉、配色、字体层级、构图、动作方式、截图或插画的使用方式。不要只给几个风格形容词。

优先提供开头、核心解释、结尾等代表性画面的设计；需要时做静帧或短预览。静态参考只能帮助选方向，不能代替动态效果。

### 同时考虑内容与素材

已有素材时，先看画风、透明度、分辨率、主体色、截图明暗和可裁切范围，再判断与目标风格的兼容性。能保留的素材通过合理的底板、裁切和分层融入画面；不适合时明确替换或处理方案。不要让单张素材的底色决定整片配色，也不要让风格词代替具体的设计。

没有现成素材时，可根据主题与受众先定视觉方向，再准备素材。涉及生成、抠图、切分或多角色状态时，按需阅读 [素材准备与复用](references/assets.md)。

- 让表现方式服务主题：机制适合示意动画，流程适合对象流转，评论适合证据与观点的清晰区分。不要把所有内容套进同一种卡片版式。
- 用户没有指定时，可提议 16:9、1920×1080、30fps；已有工程、竖屏需求和平台要求优先。字体应适配内容气质和语言，不固定为圆体或某个品牌。
- 开头尽早让观众看见问题与主体。简洁意味着信息有层次，不意味着主体很小或留白越多越好。
- 风格不满意时，检查构图、素材语言、镜头节奏和动作逻辑；只改配色往往不能解决模板感。

### 先用代表画面验证方向

新风格或改动较大时，先做一张代表性静帧或一段短预览；确实需要比较方向时，再提供少量备选。它们应覆盖最难处理的文字、素材或解释动作。用户要求先看方案时，等其确认后再铺开；已有明确方向或只做局部修改时直接沿用，不强制重新选样张。

## 3. 把每句口播转化为可见的事件

制作前阅读 [分镜与语义动画](references/storyboard.md)。把 SRT 按语义组织成连续场景，并为每条字幕记录：

> 时间与原句 → 观众要理解什么 → 主体及变化 → 动作触发 → 镜头与必要文字。

每句都要有视觉承接；可以是新动作、前一动作的结果、观察停顿或重点转移，不必每句切镜头。用户要求逐句动效时，应明确每句对应的变化，避免用全程漂浮、文字入场或同一张图推拉凑数。

优先让变化表现含义：出现原因、发生过程、状态对比、积累、分解、试错、反馈和结果。同一对象可以贯穿全片，但它应随叙事发展；重复使用静止素材不能替代发展。

一个镜头只建立一个主要注意力中心。字幕、标题、插画和镜头运动不要争夺观众。复杂机制允许逐步出现和稳定观察，动作数量不是质量指标。

## 4. 制作画面与动画

使用 Remotion 时同时使用官方 `remotion-best-practices` skill，并阅读 [实现与同步](references/production.md)。如果该 skill 缺失，参照 [环境检查与首次搭建](references/environment.md) 获取，加载与本次实现相关的指导；安装受阻时说明限制，并使用官方文档继续处理可完成的部分。现有非 Remotion 工具链合适时可沿用，不为使用本 skill 强制迁移工程。

- 图形、箭头、数值、图表、状态变化优先做成可编辑的代码或矢量元素。需要插画、纹理和人物时再生成或选取位图素材。
- 需独立运动的主体应分层。生成图片解决视觉素材，镜头与动作仍需围绕时间轴设计。
- 新闻与证据使用真实资料并注明实际来源；生成图不能冒充新闻截图、测试结果或统计证据。截图放大与高亮应准确指向相关区域并保留必要上下文。
- 画面文字保留短标题、关键词和必要标注，避免与字幕同时大段复述。关键词、公式或关键结论可以在两处出现，但要有清楚的主次关系，必要时错开时间。复杂背景上的文字使用稳定底色、局部遮罩或独立版面保证对比。
- 用目标观看尺寸检查标题、图注、截图原文和字幕。放大主体、收拢布局、裁切重点优先于堆更多装饰来填空。
- 为字幕与平台界面预留空间；关键动作、出处和说明不要躲在字幕后面。字体和素材需可随工程稳定加载。

## 5. 预览、修改与交付

按 [检查与交付](references/review-delivery.md) 检查。区分三类证据：

1. **静帧**：构图、文字大小、对比、遮挡、截图高亮位置。
2. **连续播放**：口播、字幕、动作和转场是否同步，重复与停顿是否合理。
3. **文件检查**：分辨率、帧率、时长、音轨、编码及可解码性。

不能用“构建成功”“看过几张截图”替代整片动态验收。记录实际检查范围；无法观看或听取的部分如实说明，避免宣称全部通过。

收到反馈后把感受转成具体改动：字小就改层级与尺寸；空就改主体比例与构图；动效少就补有含义的变化；素材重复就让事件演变或增加不同解释场景。修改后检查相邻镜头与所有受影响时段。

需要成片时按已授权范围导出，并验证最终文件。封面、发布标题与文案仅按需求制作，内容以最终视频为准；标题有吸引力但不扩大结论。制作发布素材不等于替用户发布到外部平台。

保留最终音频、字幕、可编辑工程、引用素材、成片及必要来源。文件命名使用主题或项目名，不硬编码期数、个人目录或机器环境。清理前先检查工程引用与共用依赖，不把删除旧文件作为默认步骤。

最终交付给出成品与工程位置、规格和实际检查结果；如有剩余问题，明确指出。
